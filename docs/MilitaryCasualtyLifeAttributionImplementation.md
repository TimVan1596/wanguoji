# 军政人物伤亡选择与死亡事实归因

版本：v0.99931q2 / package 0.99.151 / WorldSave V15  
日期：2026-10-15

## 实施范围

按已批准的方案C完成：保留围城及敌对占领导致的国家人口损耗，改为不依赖 `Team.users` 插入顺序的确定性受损者选择；为成功销毁记录会话级受损者证据；保持人物死亡、编组清理和V15权威状态语义。Stage A批准和前置v31q1人工Gate PASS均已确认。

## 根因与实现

`Team.removeOneUser()`过去按 `Set<User>` 顺序尝试销毁，因而早加入集合的User可能长期被优先选择。现在使用 `PopulationCasualtySelection.ts` 按 `factionId`、世界月份、损耗来源、可用的 `triggerCityId` 以及当前User的逻辑单位ID、MilitaryPerson ID、User ID、出生月和姓名构造稳定排序。身份缺失或冲突时不回退到集合顺序，而是不执行损耗。算法不使用系统时间、`Math.random()`或 `WorldRandom`。

围城入口仍从 `City.updateSiege()`传入真实城市ID；敌对占领入口从 `Block.setTeam()`传入 `HOSTILE_HOME_OCCUPATION`，不传虚构城市ID。原有城防伤害结算、每城伤亡间隔、每次人口扣除数量和多城独立结算均未改。

`User.destroyUser()`在真实死亡门槛通过后以运行时标记阻止重复销毁。被拒绝的君主战死判定不设置销毁标记，原君主死亡门槛仍只在该User被选中时调用一次。军事人物ID写入审计前，会核对Registry人物的 `sourceUserId`、当前势力和非死亡状态；之后继续由 `MilitaryCommandRegistry.onUserDestroyed()`处理死亡与编组。

## 归因边界与存档

成功人口损耗的会话审计记录月份、势力、原始原因、损耗来源、可选触发城市、User ID、逻辑单位ID、经核对的MilitaryPerson ID、销毁前可用的权威位置，以及人口前后数。触发城市与受损者位置分别显示。位置只是销毁时的位置快照，不能证明参战或守城；`SIEGE_LOSS`仍不代表个人战死于某城。

审计继续使用 `PopulationTransitionAudit`，最多保留最近240条，读取存档后重置，不导出、不进入WorldSave、不新增canonical历史事件。没有真实个人战斗伤亡记录时，不生成个人参战描述。V15 Schema、Exporter、Hydrator、Validator和RNG状态均未修改。

## 测试覆盖

- 稳定选择不受Set插入顺序影响；不同月份/城市上下文可产生不同确定排序；身份缺失或冲突时失败关闭。
- 生产城市围城链覆盖 `City.updateSiege()` → `Team.removeOneUser()` → `User.destroyUser()` → 军事人物/编组更新 → 会话人口审计；敌对占领链验证没有城市ID。
- 覆盖受保护君主门槛调用一次、重复销毁幂等、实际受损者位置与触发城市分开、人口前后对账及WorldRandom状态不变。
- 审计容量有界，且测试确认审计数据不进入V15 Schema、当前Schema版本仍为15。
- 测试夹具使用真实 `Team`、`User`、`City`、`Block`类及生产损耗调用路径，并为Phaser/逻辑单位提供受控运行时mock；它覆盖真实业务方法，但不是完整Phaser自然长局。

## 结果与限制

选择算法本身不改变随机流。它会改变谁承受既有损耗；人物或单位因此变化后，长局后续移动、战斗和城市易手可能自然分叉。没有在本轮执行或声称完成数百年自然多种子A/B平衡校准。围城的总人口扣除规则没有改变，也没有证据证明q1军令导致人口下降。

普通User和退役将领仍没有自然寿命更新；没有真实守城人员模型，也没有个人战场伤亡证据。若未来要求根据实际防守/交战决定个人伤亡，需独立设计守备或战斗参与机制；若要求跨读取保存个人战场暴露证据，需另行评估V16，本版不引入。
