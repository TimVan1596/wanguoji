## 审计结论

### A–B. 当前有没有持久将领及稳定军权归属？

没有。`User` 是国家人口/活动者，角色仅有 `NORMAL` 和 `RULER`。`Player` 是 Phaser 运行时对象；`Slaves`/NPC 是依附单位集合。`LogicalUnitRegistry` 给活动单位分配 `unit-N`，记录 faction、位置、速度、存活状态、可选 userId 与 rulerId，但没有编制、军队或指挥关系。玩家单位在地图上移动并参与敌对领土占领；进入城市时形成 faction 级围城接触。

`City.siegeContacts` 按进攻 faction 汇总接触次数，并保留一个可选 rulerId。`City.capture()` 会把该 rulerId 传给城市攻陷/收复事件，君主 Chronicle 可记录个人围城接触及攻城。这是**君主单位参与**的有限事实，不是稳定军队指挥权；同一 faction 的普通人口单位可以形成围城压力，且当前没有军团、编制或个人战场指挥归属。不能据此宣称游戏已有将领或军队。

### C. 能否复用现有人物？

可以复用一个已经存在且存活的普通 `User` 作为任职者，但不能把 `Ruler` 当通用人物：Dynasty 的人物同时参与继承、王统、寿命、庙谥与宗谱规则，塞入将领会错误污染王室模型。

还需补齐两个身份事实。第一，`User.id` 是活动人口 ID，只对当前存活用户查重；`destroyUser()` 会注销单位并删除用户，历史档案不保留，未来可能复用该数字。第二，普通 `User` 没有出生年月、年龄或持久死亡记录。故不能直接将 `userId` 当作永久人物 ID，也不能声称当前数据能给普通候选人准确年龄或身后履历。

推荐将**既有 User 晋任**作为首版唯一人物来源：晋任时为其分配新的稳定 `personId`，并将此 ID 绑定到该活动 User/单位；人物记录保存其姓名、出生月（须在人物生成时权威赋值）、任职/离职和死亡事实。此记录是现有 User 的军事身份延续，不生成新人物，不进入 Dynasty/继承树。普通人口仍不必全部变成永久历史人物。

### D. 真实军事作用与成果归因

首版指挥权必须实际连接现有活动 `unitId`，而非只在 UI 上挂“将军”称号。推荐建立有限编组，成员来自已经存在的单位，成员只能属于一个活动编组；指挥官本人也必须是该编组中的真实活动 User/单位。指挥命令必须被真实月度移动/占领/围城流程消费，例如编组共同执行明确的目标城市任务。没有可验证执行痕迹时，不应产生指挥成果。

当前攻城记录可支撑国家结果和城市易手，但没有通用 battle/engagement 事件。因此建议个人履历分三档：任职期间国家结果只作“任内国家事件”；已有事件明确关联其 `personId`、编组和当月时，才作本人参与；只有编组确实执行命令并对城市围攻/易手有可追踪贡献，才记作指挥结果。普通 city-captured 不应自动归功于所有当任将领。一个攻城事件已经存在时，应关联该事件，而不是每次单位接触再造一条重大世界事件。

## 设计问题 F：建议的最小权威模型

首版建议只持久化任职人物及军权，不建立全人口传记系统：

```ts
interface MilitaryPersonRecord {
  personId: string;             // 永久、世界内唯一；与 User.id 分离
  sourceUserId: number;         // 晋任时的现存人口身份，仅作交叉校验
  name: string;
  bornMonth: number;            // User 创建时记录；不从任职年龄倒推
  deathMonth?: number;          // 仅在实际 User 销毁/真实死亡时写入
  deathCause?: string;          // 仅取自实际死亡路径
  appointments: Array<{
    factionId: string;
    startMonth: number;
    endMonth?: number;
    endReason?: "DISMISSED" | "TRANSFERRED" | "FACTION_ENDED" | "DEATH";
  }>;
}

interface MilitaryFormationRecord {
  commandId: string;
  factionId: string;
  commanderPersonId: string;
  memberUnitIds: string[];      // 现存真实逻辑单位，不生成兵员
  createdMonth: number;
  order?: { targetCityId: string; issuedMonth: number };
  status: "ACTIVE" | "DISBANDED";
}
```

另需存储稳定 `personId`/`commandId` 序列，或采用有冲突校验的世界内单调 ID。Person 的任免历史以区间为准；WorldHistory 只记任命、重要离任/死亡等低频政治事件，城市战果复用原 canonical 城市事件并带可选 `commandId/personId` 归属。日常移动/接触不逐条进 WorldHistory。

这些字段必须是权威状态，因为它们决定谁有指挥权、单位受哪条命令驱动、存档恢复后如何继续。单位位置/速度和已有 faction 归属继续由现有单位 DTO 保存。水合阶段应先恢复 User 与 logical units，再校验人物记录绑定的存活 User 和 formation 的成员单位，最后恢复命令运行态；不得在水合时重新任命或生成历史事件。

出生月应在真实 User 创建时赋值，并跟随 User 持久化。当前普通人口没有年龄，不能在晋任时补造其出生史。若要给七国开局的既有人口年龄，应由新世界生成时确定，并记录为当时的模拟事实；避免仅为年龄增加 WorldRandom 抽取，建议采用不消耗 WorldRandom 的确定性初始化，或由用户另行批准具体年龄生成规则。未来实际死亡仍由现有 User 销毁路径触发军职离任和人物归档；本首版不擅自给所有人口增加自然寿命。

## 人物、军队、国家生命周期

1. **候选**：只从当月仍存在的 `NORMAL` User 中选；需满足出生月、年龄下限、在国经历/稳定性等批准后的资格。不得从亡者、历史名字、Ruler 或随机姓名池造将领。
2. **任命**：军政系统确认候选仍属该 faction，分配永久 personId，记录 appointment；同时从该 faction 当前存活单位建立有限编组并绑定指挥者。若编组无法成立，则本次任命整体不发生。
3. **服役**：编组持有的真实 unitId 列表与唯一 commanderPersonId 参与月度命令执行。单位转 faction、死亡或销毁时同步移出编组；command 不可继续引用不存在或异国单位。
4. **离任/投效**：任免写实际月份与原因；同 faction 调任可结束旧 appointment 再开始新 appointment。User 投靠/改属时，旧国编组立即解除；若新国接受任用，必须作为新 appointment，不能把国籍时间线覆盖掉。
5. **死亡**：User 的真实死亡/销毁是人物死亡唯一来源。先结束 appointment、解除编组和单位关系，再归档死亡年月/原因；不得从单位消失推测死亡，也不得因国家灭亡自动判其死亡。
6. **国家终结/流亡**：Faction 终结时编组失去有效国家命令并解散。人物仍活着；可作为无职历史人物归档。流亡/复国是否保留军职是独立政策：首版建议流亡时解除现役编组，复国后不可自动复职，须有新任命事实。
7. **改朝**：任命归属由 factionId 和实际 appointment 区间表示。异姓篡朝不自动更换现役将领归属，也不自动视为拥立/背叛；明确的改属/离任事件才改变记录。首版不允许将领影响继承、废立、篡朝。

## 两种可实施方案

| 方案 | 做法 | 优点 | 主要代价/风险 |
|---|---|---|---|
| A：轻量人物履历 | 晋任现存 User，记录将领与个人参与事件；不建立编组命令 | 改动较小；可先呈现人物和有限战斗经历 | 不能证明其拥有军权；只记录身份，未满足真实指挥玩法目标 |
| B：有限编组指挥（推荐） | 晋任现存 User；编组绑定真实 logical unitId；月度命令改变成员单位的实际目标/行为；城市事件记录实际贡献 | 人物、单位、命令和成果闭环可验证；不用伪造兵员 | 需要新增权威状态、命令消费路径、死亡/投效联动和 V15；实现与回归成本更高 |

**推荐 B。** 方案 A 不应作为本项目所称的“军权体系”交付，因为只是人物标签和履历。方案 B 是达到玩法目标的最小方案；它不是完整兵制或战斗系统，不模拟军衔、兵种、后勤、战术战斗或军队拥立。

## 容量、事件和性能边界

首版建议作为待批准的安全上限：每 faction 最多 3 名现役指挥者、最多 2 支活动编组；每编组最多 12 个现存逻辑单位，且全世界活动编组总数受国家数乘上述上限约束。任命时从已有单位中选择，不新增人口/兵员。达到上限后不任命，记录诊断计数而不反复扫描全历史。

军事人物档案仅为曾任职者创建；普通 User 不归档。每次任职写一条区间，低频任命/离任/死亡可记事件；每次普通围城接触不记事件。攻城结果在原 city-captured/city-recovered 事件上关联一个 command/person，避免一项战果重复生成多条记录。历史查询按 personId/commandId 建索引或只在人物页面打开时从现有事件索引取数；不能每帧遍历全部君主、用户和 WorldHistory。

5000 年规模需要在阶段 B 对最长世界负载做基准。上限示例：以 7 个起始 faction 为规模基线时，最多 21 名现役指挥者、14 支活动编组、168 个成员引用；历史档案增长由任命频率和国家创建次数决定，不由普通人口或每次接触决定。完整世界可能持续产生新 faction，故还应给每 faction 的历史任职区间和世界人物总数设置可观测上界/压力测试，不能默默丢弃 canonical 生涯事实。若历史档案仍增长过快，应合并同一人的连续任职区间或压缩可派生统计，不能删除权威任命事件。

## 随机数与政治边界

自动任命会影响人口/军力分配和世界走向，属于玩法模拟。候选选择、任命周期、抽签和目标命令必须使用项目现有 `WorldRandom`，并持久化周期、冷却、序列等状态。诊断、UI、历史派生和存档验证不得消耗随机数。按相同版本、种子与输入保持确定性；必须测试诊断开/关一致。不得在未获批准前确定概率或加入“陈桥兵变”脚本。

将领首版不属于 Dynasty，不进入 heirIds/houseEpochs/政治宗谱，不触发庙谥。`rulerId` 继续只代表君主。后续异姓军政夺权必须另行设计：需有真实军权积累、可归因政治危机及新的原子状态转换，不能从将领任职或一次攻城自动推断拥兵自重/黄袍加身。

## V14/V15 建议

**推荐未来阶段 B 使用 V15。** V14 能保存活动 User、逻辑单位、Ruler 和城市围城接触，但没有永久人物 ID、普通人物出生月/死亡归档、任职时间线、formation 成员引用、命令目标/冷却，也没有这些引用的 Validator/水合不变量。把新权威字段塞进 V14 的开放 JSON 对象虽可能通过宽松类型，却会绕过 schema 版本语义，且旧 V14 水合后无法可靠还原军权状态。

V15 的技术收益是可以在 Validator 中严格校验 `personId → active User/archived person`、`commandId → commander + alive member unit + faction`、任命月份和死亡边界，并在 Hydrator 中按明确顺序恢复。保存需包含人物/命令 ID 序列、人员履历、活动编组与命令状态。旧 V14 是否拒绝、是否另做导入，属于阶段 B 的存档 Gate；之前“可放弃旧存档”的批准不等于自动批准本次破坏现有 V14 长局。当前建议新 V15 不迁移 V14，只有用户单独明确批准后执行；不应现在升级或改写任何存档。

如果用户要求必须继续 V14，则需要重新缩小目标：不能保存跨死亡历史人物身份和实际指挥状态，或必须接受不完整恢复；这与本任务要求的可核验长局军权不相容。因此不推荐 V14。

## 阶段 B 实现合同（待批准）

### 最小范围

1. 加入稳定军事人物 ID 与出生月；仅由既存 User 晋任，不生成新人物。
2. 加入有限活动编组，引用现存 logical unitId；一个单位至多加入一个编组。
3. 加入任命、离任、改属、死亡的权威月度状态转换与一致性校验。
4. 将确定性目标命令接入实际月度 movement/occupation/siege 流程，使编组行为有可观察作用。
5. 在已有城市攻陷/收复事件记录真实参与的 command/person 归属；不为普通战斗接触制造重大事件。
6. 增加 WorldHistory 的低频任命/离任/死亡事实、人物档案入口和国家军政人物摘要；不扩张政治宗谱主布局。
7. V15 DTO、严格 Validator、Exporter/Hydrator、确定性 ID 序列与 round-trip。
8. 增加诊断：候选数、任命数、现役人数、活动编组/单位数、命令执行、战果归属、死亡/离任归档及上限阻断。

### 核心测试

- 从真实存在 User 任命；拒绝不存在、死亡、异国、RULER 候选；ID 永久唯一且 User.id 复用不串档。
- 真实 unitId 进入且只进入一支编组；命令实际影响月度移动/围城；无命令则行为不改变。
- 城市攻陷只归属实际有关编组/人物；任内国家战果不冒充本人战功。
- User 投靠、单位死亡、指挥官死亡、国家终结、流亡及复国时清除或结束引用，人物档案仍保留且不误判死亡。
- 5000 年活动/历史容量上限、事件增长和性能；多种子长跑报告不宣称政变成功率。
- V15 严格校验、保存→读取→继续→再保存 canonical 一致；重复水合不重复任命/历史事件。
- WorldRandom 序列一致性、诊断开关一致性、相同种子确定性；普通战争、城市攻陷、君主/宗室与现有篡朝/废立不回归。

## 可见效果、限制与人工 Gate

首版经人工观察可见：国家存在有限数量的真实姓名指挥者；人物确实由既有人口晋任；每人有任职国家和月份；其活动编组包含可在地图上识别的现存单位；命令能改变这些单位的真实目标行为；相关城市战果可回溯到实际编组；离任/死亡/国家终结后人物档案仍在。

首版不支持陈桥兵变、司马氏代魏、王莽代汉的完整历史过程，不支持政变动机、军队拥立、权臣、官职阶层、婚姻外戚、摄政、完整战斗/兵种，也不应把“将领战绩”直接转成政治合法性。未来夺权需另立版本设计 Gate。

未来人工 Chrome/Electron Gate 建议：新建世界并观察真实国家的军政人物入口；核对一名将领的姓名、出生/任职月份、Faction、真实活动单位/编组；观察一项实际命令与攻城结果归属；随后检查其离职、投效、死亡或国家终结后的归档；执行 V15 保存→读取→继续运行；检查人物页面、历史卷轴、国家档案、地图和性能。自动化测试不能替代地图/界面的人工观察。
