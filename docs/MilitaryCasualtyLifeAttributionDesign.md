## 结论摘要

建议 Stage B 采用**方案C：保留国家围城人口损耗，去除集合顺序偏差，并把人口损耗与可证实的个人参战事实分开记录和表达**。可以用当前 User、LogicalUnit、MilitaryPerson、City 与 WorldSave V15 结构完成首轮，不需要 V16；不调整城防伤害、两个月伤亡间隔或人口规则，也不为普通人口增加自然寿命。

方案C能修正“Set中靠前的人更容易被选中”以及“围城损耗等同于个人亲自战斗”的错误归因；但它不能证明遭损失的个人在受围城市，也不能把当前抽象围城损耗变成真实守城战斗。若产品要求个人只会在真实战场位置受伤亡，则需要方案A所述的守备/战斗参与模型，超出这次最小闭环。国家资源损耗与人口数量分离的方案B则需要新的权威经济/人口层，当前不推荐。

## 1. 真实调用链与围城损失语义

城市围城损耗在月度模拟中走：`AutoSimulator.advance()` → `MilitaryCommandRegistry.update()` → 各城市 `City.updateDefense()` / `City.updateSiege()` → `Team.removeOneUser("SIEGE_LOSS", context)` → `User.destroyUser()` → `MilitaryCommandRegistry.onUserDestroyed()` 与人口审计。每座城市维护自己的上次围城损耗月份；首次有效围城可造成损耗，之后须满足 `CITY_SIEGE_DAMAGE_INTERVAL_MONTHS`（当前为2个月）。一个城市的同月多次接触先汇总为一次月度判断，城防损伤及人口扣除各发生一次。

生产代码另有一条使用默认 `SIEGE_LOSS` 的路径：敌对占领带有 `isHome` 的地块时，`Block.setTeam()` 调用旧势力的 `removeOneUser()`。该调用没有触发城市ID上下文。因此 `SIEGE_LOSS`只表示这次 User 删除由围城/敌对占领损耗路径触发，不能单凭该代码将个人描述为守城战死，也不能保证每条审计都带有城市ID。

多座城的计时独立。同一世界月如果两座城分别达到各自伤害间隔，月度循环会顺序处理两个城市，守方可能损失两名不同 User；每次删除都会立即从 `team.users` 移除，因此在仍有可删除人口时不会把同一个集合成员扣两次。人口降至零后，后续调用不会再产生负人口。该并行损耗是当前规则结果，不是同一城市重复接触造成的重复计数。

## 2. 死者选择、位置与人物归因

### A. 当前选择算法

`Team.removeOneUser()`直接迭代 `Team.users` 的 JavaScript `Set`，遇到首个 `destroyUser()` 返回 `true` 的 User 就结束。它没有排序、随机抽选、位置或单位角色筛选。通常这会偏向较早加入集合且没有被转属/删除后重新加入的人；自然人口常按创建顺序加入，因而可能长期消耗相同的早期成员。此处不能简单称作“最老者先死”：集合插入顺序并不等于 `bornMonth`，且转属会删除并重新插入。

若遇到 `RULER`，`User.destroyUser()`先询问 `Core.handleRulerCombatDeath()`。该函数拒绝当前死亡时，User会被传送回去并返回 `false`，集合循环继续尝试下一个人。也就是说君主可能被保护，但其他 User 的选择仍依赖集合顺序。

### B. 位置与军事参与证据

`User`持有真实 `Player` 和 `logicalUnitId`；逻辑权威模式下，位置保存在 `LogicalUnitRegistry` 的 `LogicalUnitState.logicalX/logicalY/currentGridX/currentGridY`，V15保存单位坐标、速度、阵营和 `playerUnitId`，水合时先还原 User/Player，再安装逻辑单位。非逻辑权威模式下，运行时 Player 位置可用。City又拥有真实城池中心、围垒格和围城接触记录。

但当前 `removeOneUser()`不读取这些位置。`PopulationTransitionAudit`只记录人口前后数量、原因、月份、相关阵营及可选的触发城市字符串，没有受损 User ID 或其位置。城市 `siegeContacts` / `commandContributions`记录的是攻击接触方和进攻编组，不是守方人员。`recordCapture()`可证明某个编组贡献过真实攻陷；它不能证明该编组成员死亡，更不能证明任意守方 User 参与守城。

因此：

- 指挥官可以因为远处另一座城市的 `SIEGE_LOSS` 被选中并登记为死亡。
- 退役军事人物若仍是 `Team.users` 成员，也可能被同样选中；`RETIRED`只结束军事任职，不从人口集合中移除。
- 当前代码没有生产调用点把 `BATTLE_DEATH` 传给 `removeOneUser()`；现有军事人物死亡主要可能来自 `SIEGE_LOSS`，它不是可验证的个人战斗记录。
- `SIEGE_LOSS`不能证明死亡地点、守城行为、军令参与或直接交战。

### C. 重复销毁边界

一般围城路径同步执行：先结束/调整编组，再从 User 所属 Team 删除 User、记一次人口变化、注销 logical unit 并销毁 Player。Team 的下一座城随后看到的是更新后的集合，故不会从同一个集合再次删除该人。军事注册表在已是 `DEAD` 时不会再次创建第二条军事人物死亡事件；活动编组也会先被结束或移除成员。

不过 `User.destroyUser()`本身没有显式的“已销毁”幂等标记。若某个陈旧引用直接再次调用，它仍会再次进入清理回调、增加会话死亡诊断并尝试 dispose，但因 User 已不在集合内，不会再次减少该国人口；已死 MilitaryPerson 的状态保护避免第二条人物死亡事件。Stage B应增加针对重复调用/重叠清理路径的测试，必要时加运行时幂等防护，但不能把普通国家终结、转属或运行时 teardown 误记成死亡。

国家终结另有 `EXTINCTION_REMNANT` / `EXTINCTION_DISBAND` 删除路径，随后人物注册表目前将仍在任的军事人物转为 `RETIRED`，而不是 `DEAD`。这是有意避免把政权或运行时人口归档自动等同个人死亡的方向，但也意味着 User实体消失后，MilitaryPerson可以保留为无活跃User引用的历史人物；死亡事实没有因此得到证明。此处必须保持“人物记录归档”和“真实死亡”分离。

## 3. User年龄与寿命

新 User 构造时，`deriveUserBornMonth()`根据 WorldRandom 的稳定种子、势力ID、User ID、姓名及 spawnMonth 做稳定哈希，不消费 WorldRandom。派生年龄区间为216至742个月，即约18岁至61岁10个月；`bornMonth`允许早于世界0月。它不是模拟中的出生事件，只是给已进入世界的活动人口赋予成年年龄依据。普通 User、军事人物和君主使用不同的权威生命流程；君主有 Dynasty 的自然寿命记录与死亡更新。

普通 User 没有自然死亡更新。`PopulationSystem`负责周期性人口增长，不按 `bornMonth`淘汰或退休。军事人物任职资格要求年满18岁，但没有年龄上限，也没有“到龄退役”。只要其 User没有经人口损耗、国家终结或其他真实销毁路径移除，纯和平时期的军事人物可以在模拟中无限存活；一位40岁任职的将领可以活到200岁甚至更久。Stage B若只校准伤亡归因，应将此明确视为当前人口简化，不应顺手给所有普通人口加自然死亡率。

### 推荐的方案C规则边界

1. 保留 City 当前伤害周期、城防变化和每次一次人口扣除，不调参。
2. 选择顺序不再依赖 `Set` 插入顺序；采用稳定逻辑单位身份与（触发阵营、月份、触发城市）派生的确定性排序/轮转。多城同月会依据不同城市上下文形成稳定顺序，且前一次被删除的人已从候选中移除。不得调用 WorldRandom。
3. 受损 User ID、原阵营、人口扣除原因、月、可选触发城市可进入会话诊断，以便逐条对账；该诊断不冒充canonical战斗事件，也不回写旧历史。
4. MilitaryPerson的真实死亡月份仍来自该User实际被销毁的月份。若死亡由 `SIEGE_LOSS`触发，人物事件仅说明“围城损耗中去世”，保留原始原因代码；不附加地点、守城、参战或军令贡献，除非另有对应事实。
5. `BATTLE_DEATH`仅在真实单位战斗伤亡路径实现并产生证据后使用。当前没有该生产触发点，不应通过测试夹具假装存在。
6. 如果选择添加“附近人员优先”作为低权重候选顺序，应将其写成选择策略而非战斗证明；无在场者仍按方案C的全国人口损耗兜底。阶段B应先比较是否有必要加入这一优先级，推荐首版不加，避免引入新的位置性死亡偏差。

这一设计不消除“国家人口损耗等价于某个具体 User 被销毁”的抽象。它只保证选择公平且叙述不超出现有证据。若用户不接受个体人口损耗映射为具体人口对象，需另行批准方案B的资源模型。

## 5. 关键场景的判断

### A. 将领在A城，B城被围

当前生产规则可以删除该将领，因为Team级集合不检查位置。方案C仍可能选择他，但会依稳定候选顺序，且人物档案只记围城损耗原因，不称其在B城守城/战死。若未来要求避免这种死亡，必须采用方案A的真实驻防/战斗参与规则，不能只靠文案修饰。

### B. 两城同时被围

两城分别调用各自的 `removeOneUser()`。只要每次成功都立即从集合移除User，人口变化应逐次为 -1，User ID各不相同；审计应按城市上下文对账。若本国不足两名可销毁User，第二次可能无法减员。现有诊断记录总人口前后值及城市上下文，但不记录受损User ID；未来测试应验证逐次受害对象唯一。

### C. 将领真实参与战斗

当前军事编组通过成员实际移动、敌城围城接触及capture贡献产生可核验的**进攻方**参与证据。真实攻陷可进入指挥履历；围城人口损耗选择的是**守方全国人口**，两者不相关。没有针对某军事人物的真实单位受伤/死亡机制，因此目前不存在可证明的“该将领在战场阵亡”路径。

### D. 退役将领

退役只结束appointment/formation，人物User通常仍属于国家人口池，故仍可被国家围城损耗选中。这不等于其留在前线。方案C保留真实被销毁事实但不叙述其在场参战；方案A需要把退役与驻防资格、军职单位和生活状态关联起来。

### E. 长寿将领

无战斗或人口损耗时可以无限存活。新增全民自然寿命会影响所有 User、人口容量、军队可用单位、势力消亡、随机流、人物档案规模与V15水合语义；这应是独立的模拟设计主题，不纳入本次Stage B。当前审计未运行150年自然寿命实验；代码调用链已足以确认普通User无年龄淘汰调度。

### F. V15前后存读档

V15保存 User `bornMonth`、`militaryPersonId`、单位身份与位置；MilitaryCommandRegistry保存人物状态、死亡月份/原因、任职历史、编组成员和攻陷证据。Hydrator先恢复势力/城市/历史，再恢复Users/Units与逻辑单位，之后导入MilitaryCommandRegistry并继续模拟；Validator会检查活动军事人物与活User、编组与单位、死亡信息及事件引用。Session-only人口转换审计不写V15。

在围城损耗发生前后存读档，现有V15能保留位置、人员、编组和已登记人物死亡，读取本身不会重新抽受害者。它不能回填旧存档中缺失的受害城市/受害User ID，也不能还原过去未记录的位置证据。Stage B若只改变候选选择和会话审计，V15足够；如果要持久保存新的个人战场参与/伤亡事件元数据，则需评估V16，不可静默改语义。

## 7. Stage B建议范围与测试合同

### 最小实现范围

- 只对 `Team.removeOneUser()`的候选选择消除集合顺序偏差；保证同一世界状态、月份及触发上下文可确定重现，不调用 WorldRandom。
- 在会话人口损耗审计中记录受损User稳定身份（至少User ID与逻辑单位ID，如可得）、原势力、月份、cause和触发城市ID；清楚区分“触发城市”与“受损者位置”。不把该审计变成canonical人物参战事件。
- 保持每城围城伤害、城防、每次人口损耗数量及国家人口规则不变。
- MilitaryPerson死亡仍只在其真实User被销毁时记录；人物页面和世界事件保持中性，不把 `SIEGE_LOSS`扩写成亲自守城/战死。
- 检查 `User.destroyUser()`的重复清理保护，并确保 teardown、转属、国家终结、流亡/残部归档不伪造死亡。只在确认语义后加最小幂等防护。
- 不新增自然寿命、不引入守军/补给/兵种、不改王室人物生命周期，不新增持久化字段。

### 必需自动测试

1. User在Set插入顺序变化时，选择仍按稳定身份规则确定；跨月份/城市分布不持续伤害同一低序号人口。
2. 受损城市与受害User位置独立记录；远离城市的军事人物不得生成“在此城战死/守城”证据。
3. 两城同月真实月度路径损失两名不同User，人口审计总量与各城记录一致。
4. 城市多个单位同月重复接触仅一笔该城人口损失，伤害间隔仍有效。
5. 活动/退役军事人物被围城抽中时，死亡与任职终止年月一致，事件只写一次。
6. faction extinction的remnant、disband与transfer路径不错误标记`DEAD`；真实combat death能留下真实月份和原因。
7. 旧V15中的人物/城市/历史不回填或改写；损耗前保存、读取、损耗后保存读取均不重复死亡、重复卸编或重抽。
8. Phaser和LogicalSimulation两条生产位置路径均检查；位置判定不得被UI、诊断或水合的视觉重建改变。
9. 相同状态确定性一致，诊断开关不消费RNG；当前城市防御和人口损耗总量相同。
